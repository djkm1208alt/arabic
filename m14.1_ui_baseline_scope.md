# M14.1 — UI Baseline (mobile-first, RTL, accessible)

**Status:** Draft for review. Do not begin implementation until this is approved.

**Parent:** Inserted between M14 (Learning-object core) and M15 (Skills · levels · learning graph) in [ROADMAP.md](ROADMAP.md). Not a substitute for M24 (UI/UX & product refinement) — see §7.

This is a scoped audit-and-harden pass on the UI foundations the whole app already sits on, done now so M15–M21 build on solid ground instead of inheriting gaps.

---

## 1. Why it exists

M24 is a deliberate, full redesign pass and is explicitly "not interleaved with M15–M21" (ROADMAP.md line 43). But standing rule 3 also says accessibility is a *continuous constraint* through M15–M21, not something M24 alone is responsible for. Those two statements only work together if the baseline going into M15 is already sound.

It isn't fully sound today. The QA audit and the subsequent lang="ar" work done earlier this session found real gaps in the *current, shipped* UI:
- `lang="ar"` was added to Arabic-bearing elements only after being caught by manual audit, element by element, across several branches (M4–M16 code) — there was no systematic sweep or regression guard.
- `dir="rtl"`/`dir="ltr"` is never set anywhere in the app (grep-confirmed: only `lang` attributes were ever touched). Arabic spans are marked as Arabic but browsers are still left to infer direction from Unicode bidi rules rather than being told explicitly.
- Contrast was verified by hand during the QA audit and found fine (4.49–16.04:1) — but only *after* a false-positive scare caused by CSS transition timing, meaning there is no repeatable check, only one manual snapshot.
- Touch target sizing has never been explicitly measured against WCAG 2.5.5 (≥44×44 CSS px) anywhere in the project's history.
- Focus-visible states have never been audited as a set.

M14.1 fixes and locks down this baseline — narrowly — before M15 adds a new "Your skills" panel and M16 rebuilds `renderLearn()` on top of it, so those milestones don't need to re-litigate accessibility basics or, worse, propagate the same gaps into new UI.

## 2. What it delivers

**Not a redesign.** No new visual language, no new components, no new libraries (buildless rule holds — zero new runtime dependencies). This is a fix-what's-broken, document-what's-right pass on the *existing* design.

1. **`UI_BASELINE.md`** — a short, committed reference: the actual breakpoints already implicitly used by the app and by this project's QA process (320 / 375 / 390 / 768 / 1024 / desktop), the color tokens in use per theme with their measured contrast ratios, minimum touch-target size, and the `lang`/`dir` policy stated explicitly (see below) so future milestones don't have to rediscover it by grepping.
2. **Targeted CSS/markup fixes**, each traceable to a specific finding:
   - Add `dir="rtl"` (or `dir="auto"` where content mixes languages, e.g. a translit line) alongside the existing `lang="ar"` attributes, following the exact same "whole element yes, mid-string substring no" policy already established and applied consistently this session — extended, not reinvented.
   - Any touch target measured under 44×44 CSS px gets padded/resized.
   - Any focus state missing a visible outline gets one, consistent with the theme's existing focus styling elsewhere.
3. **`tools/a11y-audit.js`** — a small dev-time Playwright script (not shipped to the browser bundle — lives beside `tools/build-content.js` and `tools/build-audio-manifest.js`, same buildless-preserving pattern) that walks every view and:
   - measures contrast using the alpha-compositing technique proven during the QA audit (composite against the true rendered backdrop, wait past any CSS transition, not a raw RGBA read),
   - checks computed touch-target boxes for interactive elements,
   - scans for Arabic-bearing elements missing `lang`/`dir`,
   - reports at 320/375/390/768/1024/desktop.
4. **`content/m14.1-a11y-review.md`** — the one-time output of running that script against the fixed baseline, committed as evidence, matching the "before/after verification" spirit of the migration-discipline rule even though no learner-state is touched here.

## 3. Invariants — what must NOT change

| Must hold | Why |
|---|---|
| Zero new runtime dependencies, zero runtime fetches | Standing rule 5 (buildless runtime) |
| No change to `lessons`, `stepRenderers`, `progress` schema, or any `content/*.json` schema | Out of scope — this is presentation only |
| No new visual design language, no component redesign | That is M24's job, not this one |
| Every existing feature reachable exactly as before (same clicks, same keyboard paths) | Regression rule carried from every prior milestone this session |
| `dir` additions never override or fight the existing bidi behavior of mixed EN/AR strings | Must not introduce new rendering bugs while fixing old ones |

## 4. Migration requirements

None. M14.1 touches no `progress` / learner-state fields — pure presentation and markup. Standing rule 2 does not apply.

## 5. Acceptance criteria

- `tools/a11y-audit.js` runs clean (zero contrast failures, zero touch-target failures, zero missing `lang`/`dir` on Arabic-bearing elements) across all views at all six breakpoints, in both themes.
- Every fix is traceable to a specific line in `content/m14.1-a11y-review.md`'s "before" pass.
- Full regression walk (every lesson step type, both themes, keyboard-only pass) shows no behavior change — same acceptance style used for M4–M16.

## 6. Regression re-tests

Same battery already run by hand this session for every prior milestone: walk each lesson to completion (0 pageerrors), theme toggle, resize through all six breakpoints with zero horizontal overflow, keyboard-only navigation through Home → Alphabet → Vocabulary → Learn → Progress, `localStorage`-throwing resilience unaffected.

## 7. Out of scope

- Any new visual design, layout restructuring, or component work — **owned by M24**.
- Writing-system typography beyond correct `dir`/`lang` (e.g. font-pairing decisions, letter-spacing tuning for Arabic script) — **owned by M24**.
- Automated CI wiring for `tools/a11y-audit.js` (running it in a pipeline rather than by hand) — **owned by M14.5**, which formalizes tooling into a reusable harness; M14.1 ships the script, M14.5 decides how it's run going forward.

## 8. Open questions

- Should `tools/a11y-audit.js` become part of M14.5's `qa-harness.js`, or stay standalone? **Recommend:** M14.1 ships it standalone first (it has value immediately); M14.5 absorbs it into the unified harness once that harness exists, rather than M14.1 blocking on M14.5's design.
- Does `dir="auto"` ever produce worse results than an explicit `dir="rtl"`/`dir="ltr"` for the app's specific mixed-content patterns (Arabic word + parenthetical transliteration)? **Recommend:** decide per-element during implementation by testing actual rendering, not in advance — record the decision and reasoning in `UI_BASELINE.md`.

## 9. Rollout

1. Branch from current `main`.
2. Write `tools/a11y-audit.js`, run it against current `main` unmodified — this *is* the "before" snapshot.
3. Apply targeted fixes.
4. Re-run the audit — this is the "after" snapshot — write both into `content/m14.1-a11y-review.md`.
5. Write `UI_BASELINE.md`.
6. Run the full regression battery (§6).
7. Open a draft PR with the before/after audit output in the description.
8. Merge on your explicit approval.
