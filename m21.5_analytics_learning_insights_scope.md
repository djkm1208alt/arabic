# M21.5 — Analytics & Learning Insights

**Status:** Draft for review, implemented in the same pass per standing direction — see rollout note.

**Parent:** Depends on M19 (Review / retention, merged via a separate PR chain) and M19.5 (Local Learner State, this branch). Re-grounded against both real implementations before writing this revision.

A **local-first-only** insights panel on top of M19's review data and M19.5's companion event store. No aggregate/cross-learner telemetry — that half is explicitly deferred to M22+.

---

## 1. Why this revision exists

The original scope doc assumed M19.5's IndexedDB stores held `reviewState`/`interactionEvents` as the *primary* data source with indexes purpose-built for a "weakest-N" query. The real, merged M19 + this branch's (re-scoped) M19.5 are different:

- `progress.reviewState` lives in memory/`localStorage` (plain object, not IndexedDB) — and that's fine. At the current and near-future object count (234 today, low thousands at full A1–C2), a synchronous `Object.values(progress.reviewState)` filter is not a performance problem IndexedDB needs to solve. `reviewQueue("weak")` (M19's own function) already answers "weakest objects" directly — no new query layer needed.
- M19.5's IndexedDB store holds *raw interaction events*, unbounded, but only queryable **per object** (`getFullInteractionHistory(objectId)`) — there was no "all events, chronological" query, because nothing needed one yet. This milestone adds one (`getAllInteractionEvents()`), used only by the export feature.
- Rendering the panel itself stays **synchronous**, driven by `progress.interactionLog` (the capped 400-event in-memory log — plenty for a first trend/streak view) and `progress.reviewState` (uncapped, already in memory) — matching `renderProgress()`'s existing fully-synchronous pattern, rather than introducing an async-render code path into a view that everywhere else renders instantly. The **export** feature is the one place this milestone reaches into IndexedDB for the deeper, unbounded history — a natural fit, since export is already a discrete, user-initiated action rather than something on the render-critical path.

## 2. What it delivers

No new libraries — inline-SVG charts, consistent with the buildless rule.

1. **A new Progress-view panel** ("📊 Your insights"), same pattern as M15's "Your skills" panel: one `renderInsightsPanel()` + CSS scoped to `#view-progress`.
2. **Time-per-strand** — `skillPracticeTime()` aggregates `count` and `timeMs` (summed `latencyMs`, when known) per skill from `progress.interactionLog`.
3. **Accuracy trend** — `accuracyTrend()` buckets the capped `interactionLog` chronologically (8 buckets) and computes accuracy % per bucket, rendered as an inline-SVG bar chart. Returns `null` (→ "not enough data yet") under a minimum sample size.
4. **Weakest-N objects** — reuses M19's own `reviewQueue("weak")` directly (objects currently `weak`/`forgotten`), framed as "Focus areas," not a failure list.
5. **Practice-activity chart** — `activityByDay()` buckets `interactionLog` by calendar day, rendered as an inline-SVG sparkline for however many recent days are actually present in the capped log (honest about the log's own bound — this is "recent activity," not a lifetime streak history).
6. **"Export your data as JSON"** — assembles the current `progress` snapshot plus, asynchronously, the *full* unbounded interaction history from M19.5's IndexedDB store (`getAllInteractionEvents()`, new) — a strict superset of what the panel itself shows, triggered as a real file download (`Blob` + `URL.createObjectURL` + a synthetic `<a download>` click — no existing pattern in the app to follow, so introduced fresh here, and revoked after).

## 3. Invariants — what must NOT change

| Must hold | Why |
|---|---|
| No fabricated numbers — every metric is either real or explicitly "not enough data yet" | Standing rule 4/5, extended from skills to analytics |
| New CSS confined to `#view-progress` | Established invariant from M15's panel |
| No new libraries | Standing rule 5 |
| No data leaves the device | Local-first only |
| Panel render stays synchronous | Matches `renderProgress()`'s existing pattern; only export touches IndexedDB |

## 4. Migration requirements

None. Purely additive reads over M19/M19.5's existing data; no new persisted learner-state field.

## 5. Acceptance criteria

- Every number in the panel traced to a synthetic, known interaction history and confirmed against a hand-computed expectation.
- Fewer than the minimum sample size → honest "not enough data yet," never a zero presented as real.
- Export produces valid JSON; round-tripped against live `progress` + IndexedDB state and confirmed complete.
- Panel renders correctly at all six breakpoints; `tools/qa-harness.js` full regression and `tools/a11y-audit.js` both pass.

## 6. Out of scope

- Any cross-learner aggregate or telemetry — deferred in full to M22+, per standing policy.
- Any UI outside the one Progress-view panel.
- Predictive/prescriptive recommendations — M25+'s job.
- Deeper trend analysis using the full IndexedDB history for anything beyond export — the render-time trend/streak views intentionally stay on the always-available, synchronous 400-event log; a future milestone can revisit this once there's a real reason the capped log isn't enough for the panel itself, not just for export.
