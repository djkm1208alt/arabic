# M19.5 — Local Learner State (IndexedDB)

**Status:** Draft for review, implemented in the same pass per standing direction — see rollout note.

**Parent:** Depends on M19 (Review / retention), which is now genuinely merged into `main` via a separate PR chain (#16/#17) — a different, independently-built implementation than the one this scope doc originally assumed. This revision re-grounds the plan in the real, merged M19 before implementing.

---

## 1. Why this revision exists

The original version of this scope doc (written before M19 existed in the codebase) proposed a full storage-engine swap: move `progress` wholesale from `localStorage` to three IndexedDB object stores, with the app's synchronous `progress` global becoming an async-hydrated cache. That plan was designed against an *assumed* M19 shape.

The real, merged M19 is different in a way that changes the right scope here:

- `progress.interactionLog` is a **capped ring buffer (400 events)**, not an unbounded array — the other PR chain already solved "an event log can't grow forever in one blob" pragmatically, by capping it and using an incremental cursor (`progress.reviewCursor`) so `foldReviewState()` never needs to re-read dropped events. The urgent problem M19.5 was written to solve is already mitigated, not absent.
- `progress.reviewState` is **not** capped (one record per object ever interacted with) and every `saveProgress()` call re-serializes the *entire* `progress` blob via `JSON.stringify`. As vocabulary scales toward A2–C2 (M21), this is the part that actually gets expensive — not the interaction log.
- A full async rewrite of `progress` touches the ~50+ existing call sites that read it synchronously at boot and throughout every view, for a problem that (per the two points above) is now narrower than originally assumed. That's a large blast radius for a shrunken problem.

**Revised scope:** IndexedDB becomes a durable, unbounded **companion store** for interaction history — not a wholesale replacement of `progress`'s synchronous, in-memory, `localStorage`-backed role. The capped `interactionLog` keeps doing exactly what it does today (nothing about `emitInteraction`, `foldReviewState`, `mistakes()`, or any UI consumer changes); IndexedDB additionally, asynchronously, and non-blockingly captures every event forever, giving M21.5's future analytics work (and any future "your full history" feature) something better than 400 events to work with. This is a smaller, safer change that still solves the real forward-looking problem, and is disclosed here as a deliberate departure from the original plan, the same way M15.5 and M20.5 each adapted once grounded in real code.

## 2. What it delivers

Native IndexedDB, zero new npm package (a small hand-written wrapper, matching `safeStorageGet`/`safeStorageSet`'s naming and defensive-fallback convention).

1. **`safeIdb*` wrappers** — `safeIdbOpen()`, `safeIdbPut(store, value)`, `safeIdbGetAll(store)`, `safeIdbCount(store)` — each a Promise, each resolving to a safe no-op/empty result (never throwing) if IndexedDB is unavailable, blocked, or errors (private browsing, quota, disabled storage — the exact resilience pattern already shipped for `localStorage`).
2. **One object store, `interactionEvents`** (autoIncrement key, indexed on `objectId` and `ts`) — a durable, unbounded mirror of every event `emitInteraction()` records. Written asynchronously, fire-and-forget, from inside `emitInteraction()`; never read from on any synchronous/boot path, so it cannot introduce a timing regression.
3. **One-time backfill**: on first load post-M19.5, whatever is currently in the capped `interactionLog` (up to 400 events — an honest partial backfill, since that's the entire history that exists) is copied into IndexedDB. Versioned and idempotent (a `localStorage` flag marks it done, checked before ever re-running).
4. **`getFullInteractionHistory(objectId)`** (async) — queries IndexedDB's `objectId` index for every event ever recorded for one object, not just whatever survived the 400-event cap. The concrete, usable deliverable this milestone exists to provide for M21.5.
5. **`content/m19.5-local-learner-state-review.md`** — verification: the backfill migration, idempotence, and a query proving history beyond 400 events survives once the cap would otherwise have dropped it.

## 3. Invariants — what must NOT change

| Must hold | Why |
|---|---|
| Zero change to `emitInteraction`, `foldReviewState`, `reviewQueue`, `mistakes`, `retainedSet`, or any UI consumer of `progress` | This is additive, not a rewrite — the entire existing M19 system keeps working exactly as merged |
| `progress` stays synchronous, in-memory, `localStorage`-backed | The original plan's async rewrite is exactly what this revision is avoiding — see §1 |
| A learner on a browser/context where IndexedDB is unavailable has an identical experience to today (the companion store silently isn't populated; nothing else is affected) | Matches the existing resilience philosophy |
| Zero new runtime dependencies | Standing rule 5 |

## 4. Migration requirements

| Requirement | How it's met |
|---|---|
| Migration function | `backfillInteractionEventsToIdb()`, versioned via a `localStorage` flag, runs once |
| Before/after verification | Seed a synthetic `interactionLog`, run the backfill, confirm every event round-trips into IndexedDB with no loss and no duplication on a second run |
| Rollback safety | `localStorage`'s `interactionLog`/`reviewState` are untouched by this milestone — IndexedDB is additive, so there's nothing to roll back *from* |

## 5. Acceptance criteria

- Backfill is idempotent — running it twice produces the same IndexedDB row count as running it once.
- `getFullInteractionHistory(objectId)` returns more than 400 events for an object once more than 400 interactions have occurred for it (proven with a synthetic dataset, since real usage won't reach that volume yet).
- A simulated IndexedDB failure (blocked/unavailable) degrades to "the companion store just isn't populated" with zero visible effect on any existing feature.
- `tools/qa-harness.js` full regression passes unchanged; `tools/a11y-audit.js` clean (no UI is added by this milestone).

## 6. Out of scope

- Moving `reviewState` or `progress` itself into IndexedDB as the primary store — the narrower, lower-risk companion-store design in §1 replaces that plan.
- Any UI — this milestone ships a queryable data layer for M21.5 to build on, not a panel of its own.
- Un-capping the in-memory `interactionLog` itself — it keeps its existing 400-event role unchanged; IndexedDB is where unbounded history now lives.
