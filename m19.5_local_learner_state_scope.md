# M19.5 — Local Learner State (IndexedDB schema)

**Status:** Draft for review. Do not begin implementation until this is approved.

**Parent:** Inserted between M19 (Review / retention) and M20 (Content pipeline + complete A1) in [ROADMAP.md](ROADMAP.md).

This migrates the storage *engine* underneath `progress` from a single `localStorage` blob to IndexedDB, before M20/M21's content scale-out makes the event log large enough for that to matter.

---

## 1. Why it exists

M19 introduces `InteractionEvent` (one record per graded interaction) and per-object `ReviewState`. That's a fundamentally different data shape from everything `progress` has held before it — `mastered`, `lastStudied`, `streak`, `quizBest`, etc. are all small, low-cardinality fields that comfortably fit in one JSON blob under `localStorage`. An append-only event log, growing with every graded interaction across a curriculum that will eventually span A1–C2 (M21), does not fit that pattern well: every write re-serializes and re-writes the *entire* blob, and every read of "this object's review state" or "events for the last 30 days" requires loading and scanning everything.

M19.5 exists specifically at this point — after M19 defines the shape, before M20/M21 generate the volume — so the migration happens once, on a schema that's already settled, rather than being forced later under content-scale pressure or skipped entirely until it becomes a performance problem.

## 2. What it delivers

Native IndexedDB — zero new npm package (deliberately not the `idb` convenience wrapper; a small hand-written promise wrapper instead, to keep the "zero runtime dependencies" rule unambiguous and to mirror the project's existing `safeStorageGet`/`safeStorageSet` naming and defensive-fallback convention exactly).

1. **Schema** (one IndexedDB database, three object stores):
   - `reviewState` — keyed by object id; one record per learning object with its current `ReviewState` (M19's `learned → practised → weak → forgotten → reviewed → retained` state plus `dueDate` and related scheduler fields).
   - `interactionEvents` — append-only log, auto-incrementing key, indexed on `objectId` and `timestamp` for the queries M19's review queues and M21.5's insights panel both need.
   - `progressMeta` — the small, low-cardinality fields that were always a good fit for a single blob (`streak`, `dailyGoal`, `dailyProgress`, `skillLevels`, `placementResult`, theme preference, etc.) — stays **one record**, deliberately not normalized further, since none of that data has the volume problem the event log has.
2. **`safeIdb*`-style wrappers** (`safeIdbGet`, `safeIdbPut`, `safeIdbQuery`, etc.) — same try/catch-and-degrade philosophy as `safeStorageGet`/`safeStorageSet`, with an in-memory fallback if IndexedDB is unavailable or throws (private-browsing restrictions, quota errors, disabled storage), matching the exact honesty/resilience pattern already shipped for the Critical-#1 localStorage fix earlier this session.
3. **One-time, versioned, idempotent migration** from the existing `localStorage` blob into the new IndexedDB stores, run once on first load after this milestone ships. The original `localStorage` blob is **left in place as a legacy snapshot**, not deleted — cheap insurance, consistent with how migrations have been handled throughout the project (never destroy the only copy of learner data).
4. **Async-propagation audit**: `localStorage` access has always been synchronous; IndexedDB is inherently asynchronous. Every call site that currently reads `progress` synchronously (there are many, across every `stepRenderer` and view) needs auditing for whether it can tolerate becoming async, and the wrapper API needs to be designed so the common "read once at view-render time" pattern stays simple (e.g. resolve to an in-memory cache after first load, so most call sites don't need to become `async` themselves).

## 3. Invariants — what must NOT change

| Must hold | Why |
|---|---|
| The **logical** `progress` contract (field names, shapes) stays identical to every call site outside the storage layer | This is an engine swap, not a data-model change — M15's `deriveLevel`, M16's lesson generator, etc. must not need to change |
| No learner ever loses existing progress | Standing rule 2 (migration discipline) — non-negotiable |
| A learner on a browser/context where IndexedDB is unavailable still has a working (in-memory or localStorage-fallback) experience for that session | Matches the existing resilience philosophy already shipped for storage failures |
| Zero new runtime dependencies | Standing rule 5 — hand-written wrapper, not the `idb` package |

## 4. Migration requirements

| Requirement | How it's met |
|---|---|
| Migration function | A dedicated `migrateProgressToIndexedDb()`, run once, versioned (so it never re-runs against an already-migrated learner) |
| Before/after verification | Seeded-RNG byte-compare pattern, same as M14's `migrateMastered` — construct a representative `progress` blob, run the migration, verify every field round-trips into the new stores with no loss |
| Rollback safety | Legacy `localStorage` blob is retained, not deleted, so a failed migration can fall back to the pre-M19.5 read path without data loss |

## 5. Acceptance criteria

- Migration is idempotent — running it twice produces the same end state as running it once.
- Every existing call site that reads/writes `progress` continues to function with no behavioral change (verified via M14.5's `qa-harness.js` full regression walk, if that milestone has landed).
- A simulated IndexedDB failure (quota exceeded, blocked, or unavailable) degrades gracefully to the in-memory fallback rather than crashing — matching the existing `localStorage`-throwing resilience test already in the QA battery.
- Query performance for "all due review items" and "last 30 days of events" is demonstrably better than a full-blob scan once the event log has non-trivial volume (a synthetic large dataset used for this check, since real volume won't exist yet).

## 6. Regression re-tests

Full lesson walk-through (all step types), theme toggle, mid-lesson reload resilience, `localStorage`-unavailable AND IndexedDB-unavailable resilience (both simulated), full `progress`-reading feature set (skills panel, progress view, streak display) verified against migrated data.

## 7. Out of scope

- Any change to M19's actual `InteractionEvent`/`ReviewState`/scheduler *logic* — that's M19's own deliverable; M19.5 only changes where that data lives, not how it's computed.
- Cross-device sync — **owned by M22**, which is the first milestone allowed to touch a backend at all (standing rule / "Explicitly deferred" list: "Backend / accounts / sync → M22. Any earlier is an empty shell."). M19.5 is explicitly a **local-only** storage-engine change; it makes M22's eventual sync easier (indexed records diff far better than one giant blob) but does not pull any of M22's backend work earlier.
- M21.5's insights queries themselves — M19.5 only ensures the indexes exist to make them fast; the panel and its queries are M21.5's own deliverable.

## 8. Open questions

- Should the hand-written IndexedDB wrapper live inline in `index.html` (consistent with the single-file buildless philosophy) or as a separate dev-time-compiled module? **Recommend:** inline, same as everything else in the app — there's no build step to justify splitting it out, and the buildless rule is about the shipped artifact, not source organization preference.
- What triggers the one-time migration — app load, or a specific version-check gate? **Recommend:** a version-check gate (a small `SCHEMA_VERSION` constant checked on load), so it runs exactly once per learner regardless of how many times the app is opened, and so future schema changes have a precedent to follow.

3. Write the `safeIdb*` wrapper layer with in-memory fallback.

5. Audit and update call sites for async propagation, minimizing surface area via the in-memory-cache-after-first-load pattern.
6. Full regression battery (§6), including simulated storage-failure paths.
7. Open a draft PR.
