# M20.5 — Arabic Language Tools (spellcheck, morphology, diacritization)

**Status:** Draft for review. Do not begin implementation until this is approved.

**Parent:** Inserted between M20 (Content pipeline + complete A1) and M21 (Content scale-out) in [ROADMAP.md](ROADMAP.md).

Small, curated, learner-facing Arabic-processing tools scoped tightly to the app's own content — deliberately **not** a general-purpose NLP/morphology engine.

---

## 1. Why it exists

Two concrete gaps exist today, both grounded in the actual code and content already in the repo:
- `stripArabicDiacritics()` (confirmed at `index.html:4995`, in use since Milestone 1 by `findExampleWord`) already does mechanical ḥarakah-stripping for one purpose. `content/texts.json`'s `reduced`/`unvowelled` fields (confirmed schema: `id, kind, textType, source, vowelled, reduced, unvowelled, translit, en, words[], audio, level, skills, prereqs`) are currently **hand-authored** — meaning they can silently drift out of sync with `vowelled` with no automated check.
- The app currently has **zero free-text input surfaces** (a finding from the earlier security audit). M18 is about to add `build-word`/`build-sentence`/`dictation` exercise types, all of which will need to accept and fairly grade free-typed Arabic — which requires normalizing alef variants (أ/إ/آ/ا) and tāʾ marbūṭa/hāʾ confusions before comparison, or every learner who types a normatively-equivalent-but-not-byte-identical answer gets marked wrong.

M20.5 sits right after M20 (once the content pipeline is mature and a real corpus — A1 complete — exists to validate against) and right before M21's scale-out, so these tools can be cross-checked against real content immediately and then carried forward as every subsequent level is authored.

## 2. What it delivers

Three narrowly-scoped pieces, each explicit about what it is *not*:

1. **`normalizeArabicInput()`** — alef-variant and tāʾ marbūṭa normalization, generalizing the existing `stripArabicDiacritics` pattern (same file, same style, extending a proven function rather than introducing a new dependency). This is preparation for M18's free-text exercise types — M20.5 ships the normalizer; M18 (or whichever milestone actually builds `build-word`/`build-sentence`/`dictation`) wires it into grading. If M18 has already landed by the time M20.5 starts, this ships directly into its grading path instead of waiting.
2. **`content/roots.json`** — a small, hand-curated root/pattern table, scoped to the actual lexeme set (confirmed ~200–400 entries in `content/lexemes.json`), used only to generate plausible confusable-root distractors for quiz items. Every entry is manually checked against real sources before inclusion — **not** an algorithmic morphological analyzer, and not attempting to cover Arabic root/pattern morphology in general. This is the "never invent Arabic" rule (standing rule 1) applied directly: a general derivational engine would eventually generate a real-looking but wrong root/pattern combination; a curated table checked entry-by-entry cannot.
3. **`deriveReducedForm(vowelled)` / `deriveUnvowelledForm(vowelled)`** — mechanical derivation functions (Unicode ḥarakah-stripping, generalizing `stripArabicDiacritics` the same way as (1)), wired into M14.5's `tools/build-content.js --lint` as a cross-check: flag any `content/texts.json` entry where the hand-authored `reduced`/`unvowelled` field doesn't match the mechanically-derived one. This doesn't replace hand-authoring (a human still writes the canonical `reduced`/`unvowelled` form, since some reductions are stylistic, not purely mechanical) — it catches drift and typos.

Explicitly **not** "spellcheck" in the request's literal sense — a real dictionary-backed Arabic spellchecker (checking whether a free-typed word is a valid word at all, as opposed to matching an expected answer) is a materially bigger scope, flagged in §7 as separate future work, not silently absorbed into this milestone.

## 3. Invariants — what must NOT change

| Must hold | Why |
|---|---|
| `content/roots.json` entries are 100% human-checked against real sources before merge | Standing rule 1 — never invent Arabic, no exception for "just distractors" |
| `deriveReducedForm`/`deriveUnvowelledForm` never silently overwrite hand-authored fields | They're a lint check (M14.5-style), not an auto-fixer — a mismatch is a flag for human review, not an automatic rewrite |
| `normalizeArabicInput()` normalizes for *comparison* only, never mutates what's displayed back to the learner | A learner's own typed input should never be silently rewritten in front of them |
| Zero new runtime dependencies | Standing rule 5 |

## 4. Migration requirements

None. No `progress` / learner-state schema touched — this is content-tooling and a pure function addition.

## 5. Acceptance criteria

- `normalizeArabicInput()` correctly equates the standard alef-variant and tāʾ marbūṭa confusable pairs on a hand-built test set of real example words drawn from `content/lexemes.json`.
- `content/roots.json` passes the same "checked against real sources" bar as every other piece of Arabic content in the project — each entry cited, not generated.
- `build-content.js --lint` (from M14.5) flags at least one deliberately-introduced `reduced`/`unvowelled` mismatch in a scratch copy of `content/texts.json`, and passes clean against the real, current content.
- Confusable-root distractors generated from `roots.json` are spot-checked by hand for a sample of quiz items and confirmed genuinely plausible-but-wrong (the actual pedagogical purpose), not nonsensical.

## 6. Regression re-tests

`build-content.js`'s normal compile output unaffected by the new `--lint` cross-check (warn-only, same as M14.5's own lint additions). Full content compile still succeeds against current `content/*.json` with zero errors.

## 7. Out of scope

- **A real dictionary-backed Arabic spellchecker** (validating whether free-typed input is any valid Arabic word, not just matching an expected answer) — materially larger scope (needs a real lexical resource, not a curated ~300-entry table); flagged as separate future work, not part of this milestone.
- **General morphological analysis** (deriving root/pattern for arbitrary Arabic text) — deliberately out of scope; `roots.json` only covers the app's own curated lexeme set.
- **Automated diacritization of un-vowelled input** (adding ḥarakāt to text that doesn't have them — the much harder, genuinely research-grade direction) — this milestone only goes the easy, mechanical direction (vowelled → reduced/unvowelled by stripping), never the hard direction (unvowelled → vowelled by inference). Full automatic diacritization is not attempted anywhere in this plan.
- Wiring `normalizeArabicInput()` into M18's actual grading logic, if M18 hasn't landed yet — ships as a ready-to-use function; integration happens wherever `build-word`/`build-sentence`/`dictation` actually gets built.

## 8. Open questions

- Should `content/roots.json` be authored fresh for this milestone, or should it wait until M21's scale-out produces a larger, more representative lexeme set? **Recommend:** author it now, scoped to the ~200–400 lexemes that exist post-M20 (A1 complete) — a smaller curated table for a smaller vocabulary is easier to fully verify than a larger one attempted later, and it can grow incrementally as M21 adds levels, following the same "checked before merge" discipline each time.
- Does `deriveReducedForm`/`deriveUnvowelledForm`'s mismatch-flagging belong in M14.5's linter directly, or as a separate M20.5-owned check invoked from the same `--lint` pass? **Recommend:** implemented in M20.5 (since it needs the Arabic-specific derivation logic this milestone owns) but registered into M14.5's existing `--lint` pass rather than creating a second, parallel lint entry point — one lint command, contributions from multiple milestones.

3. Author `content/roots.json`, checking each entry against real sources; generate and spot-check sample distractor sets.
4. Write `deriveReducedForm`/`deriveUnvowelledForm`; register the cross-check into `build-content.js --lint`.
5. Run the cross-check against real `content/texts.json`; investigate and resolve any genuine mismatches found (fixing the hand-authored field, not the derivation).
6. Full regression battery (§6).
7. Open a draft PR.
