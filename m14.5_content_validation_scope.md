# M14.5 — Content Validation Framework (QA pipeline)

**Status:** Draft for review. Do not begin implementation until this is approved.

**Parent:** Inserted between M14 (Learning-object core) and M15 (Skills · levels · learning graph) in [ROADMAP.md](ROADMAP.md). Overlaps in spirit with M20's "linguistic linter" — see §7 for the explicit split.

This formalizes, into a repo-committed and reusable tool, the manual QA process that has been performed by hand — carefully, but by hand — for every milestone this session.

---

## 1. Why it exists

Every milestone so far (M4–M16) was verified the same way: launch the app under Playwright, walk every lesson to completion, resize through breakpoints, toggle themes, check the console for errors, grep for regressions. That process caught real bugs (localStorage crashes, the `#lesson` hash crash, missing `lang="ar"`, a stale CTA). It also depended entirely on a human — this session — reconstructing the checklist from memory each time.

Two structural problems that get worse as content grows (M15 adds skills/levels, M16 adds a full curriculum tree, M20–M21 add complete content for A1 through C2):
1. **Structural content bugs** (a dangling `prereqs` id, a duplicate object id, a `curriculum` node pointing at a lesson that doesn't exist) are currently only caught if someone happens to notice — `tools/build-content.js` compiles content but doesn't validate its internal consistency.
2. **Regression QA** (the Playwright walk-through) has no committed form. It's been re-derived from scratch, correctly, each time — but that's fragile and doesn't scale to a "continuous content operation" (M21's own description of itself).

M14.5 exists now, before M15's data model and M16's curriculum tree both land, so the linter and harness can validate them from the moment they exist rather than being retrofitted after two more milestones of content.

## 2. What it delivers

Two independent pieces, kept separate because they check different things:

**(a) `tools/build-content.js --lint` mode** — structural validation, run at compile time:
- every id referenced (`prereqs`, `examples`, curriculum `objects`/`children`) resolves to a real object — no dangling references,
- no duplicate ids within or across `content/*.json` files,
- every `LETTERS`/`MARKS`/`SYLLABLE_OBJECTS` entry that should carry ḥarakāt actually has them present (coverage check, not correctness — correctness is a human/linguistic judgment, out of scope here),
- every object referenced by `content/curriculum.json` exists in the compiled learning-object set.
- Zero new dependencies — pure structural traversal of the same JSON already being compiled, buildless-preserving.

**(b) `tools/qa-harness.js`** — a Playwright-based regression suite codifying the exact battery already proven by hand this session:
- walk every lesson (all step types: `explain`, `example-set`, `practice-choice`, `quiz`, `trace-letter`, `reading-practice`, `audio-exercise`, `listen-repeat`, `complete`) to completion, asserting 0 `pageerror` events,
- 0 horizontal overflow at 320/375/768/1280,
- `lang`/`dir` coverage scan across all views (reusing M14.1's `tools/a11y-audit.js` logic where it applies — see M14.1 §8),
- both themes render without console errors,
- `localStorage`-throwing resilience (matching the QA-audit fix pattern already shipped),
- mid-lesson page reload doesn't crash (the `#lesson` hash guard already fixed).

This is explicitly **the project's first npm devDependency** (Playwright as a `package.json` devDependency rather than an ad-hoc `NODE_PATH=/opt/node22/...` invocation). It only affects the dev/CI environment — standing rule 5's "zero runtime dependencies" is about what ships to the browser, which this does not touch. Flagged as an open question below rather than assumed, since it's a first for this repo.

## 3. Invariants — what must NOT change

| Must hold | Why |
|---|---|
| Zero new runtime (browser-shipped) dependencies | Standing rule 5 — dev tooling is explicitly exempted, runtime is not |
| `build-content.js`'s existing non-lint compile behavior is unchanged | `--lint` is additive, not a replacement of the compile step M14 already shipped |
| The harness only *observes* app behavior — it never becomes a code path the shipped app depends on | Keeps the harness a QA tool, not a hidden runtime dependency |
| Existing manual QA process this session used remains reproducible even if the harness isn't run | Defense in depth — the harness codifies, it doesn't replace judgment |

## 4. Migration requirements

None. No `progress` / learner-state schema touched.

## 5. Acceptance criteria

- `tools/build-content.js --lint` catches a deliberately-broken example (a dangling id, a duplicate id, a missing ḥarakah) introduced into a scratch copy of `content/*.json` — this mirrors M20's own stated acceptance bar ("the linter catches a deliberately-broken example") for the structural subset M14.5 owns.
- `tools/qa-harness.js` run against current `main` passes clean, and is proven to *fail* when a known-bad change is deliberately reintroduced (e.g. temporarily removing the `localStorage` try/catch) — a negative control, not just a happy-path run.
- Both tools documented with a one-line `npm run` invocation each.

## 6. Regression re-tests

Running the harness itself *is* the regression re-test for this milestone — its own existence is what's being validated. Additionally, confirm `build-content.js`'s normal (non-lint) compile output is byte-identical before and after adding `--lint` mode.

## 7. Out of scope

- **Linguistic/grammar linting** (register, transliteration↔Arabic consistency, level-fit, natural usage) — **owned by M20**, which explicitly scopes a "linguistic linter" as part of the content pipeline milestone. M14.5 owns *structural* validation only (do ids resolve, are there duplicates, is coverage present); M20 owns whether the *Arabic itself* is correct. This split is deliberate: M14.5 needs no linguistic judgment and can ship now; M20's linter needs the mature pipeline this milestone is a precursor to.
- CI/pipeline wiring (running the harness automatically on every push) — worth doing eventually, but this milestone ships the tools; whether/how they run unattended is a separate decision once the team's actual workflow (solo iteration vs. PR-gated CI) is clearer.
- Automated visual regression / screenshot diffing — no such infrastructure exists yet; out of scope until a real need for it appears.

## 8. Open questions

- Is adding Playwright as a committed `package.json` devDependency (vs. the current ad-hoc invocation) acceptable? **Recommend:** yes — it's dev-only, doesn't touch the shipped runtime, and removes the current dependency on a specific pre-installed environment path (`NODE_PATH=/opt/node22/...`), making the harness portable to any contributor's machine.
- Should `--lint` block `build-content.js`'s normal compile on failure, or just warn? **Recommend:** warn-only for now (non-blocking), since the pipeline is young and a hard block could stall unrelated work; revisit as blocking once M20's fuller pipeline exists and the team trusts the linter's signal.

## 9. Rollout

1. Branch from current `main`.
2. Add `--lint` mode to `tools/build-content.js`; verify against current `content/*.json` (should pass clean — no known structural bugs today).
3. Introduce a deliberate structural bug in a scratch copy; confirm `--lint` catches it; revert.
4. Write `tools/qa-harness.js`, covering the battery in §2(b).
5. Run it against current `main`; confirm clean pass.
6. Negative-control test per §5; confirm it fails as expected; revert the deliberate breakage.
7. Add `package.json` (first one in this repo) scoped to devDependencies only.
8. Open a draft PR.
9. Merge on your explicit approval.
