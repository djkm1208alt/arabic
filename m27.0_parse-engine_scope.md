**One-line summary:** Add one exercise type — `parse` — that lets a learner tag a highlighted word
in a sentence with its grammatical role and case, graded from an optional `iʿrāb` annotation array
authored on `texts.json` entries. Add a `term:` learning-object kind and a `content/metalang.json`
glossary for the naḥw metalanguage those lessons need, with an inline tooltip. Ship the capability
plus fixtures — **no real iʿrāb lesson, no B1/B2 content, no `grammar.json` change.**

M27.0 is the engine. M27.b1 (its own scope doc) authors the first real B1 labelling lesson against
it.

---

## 1. Why M27.0 exists

The `exerciseTypes` registry (M18) has `choice` / `match` / `cloze` / `build` / `order`. None can
ask *"what is the role of this word, and what case is it in?"* — the single operation every iʿrāb
lesson is built on. Without it an "iʿrāb lesson" degrades to passive reading, which the M27 audit
(`reference/iraab-audit.md` §9) calls out as defeating the purpose. M27.0 is the smallest change
that makes analytical iʿrāb teachable: one exercise type, one optional annotation field, one small
glossary. It parallels exactly how M18 added `build` / `order` — a registry entry plus a generator
plus a validation check, no authored question file.

The naḥw metalanguage (مُعرَب, مَبنيّ, عَلامة, مَحَلّ, مرفوع/منصوب/مجرور …) is itself a teaching
dependency the project has never had as addressable objects. M27.0 gives it the same treatment
`marks.json` gave the ḥarakāt: a small typed table, compiled to a lookup, linkable from lessons.

## 2. What M27.0 delivers

### 2.1 `exerciseTypes.parse` — the registry entry

A new entry in the existing registry, same `render(item, host, onResult)` contract as every M18
type, `selfManaged: false` (so `renderExerciseStep` owns the daily-goal bump and the interaction
emit), `strands: ["grammar"]`.

```
{
  type: "exercise",
  exercise: {
    kind: "parse",
    skill: "grammar",
    objectIds: [ ...gr: / txt: ids ... ],
    prompt: "Tag each highlighted word.",
    sentence: "الْبَيْتُ كَبِيرٌ",          // the vowelled string, from the source text
    tokens: [                               // one per word the learner must tag
      { i: 0, surface: "الْبَيْتُ", ask: ["role","case"] },
      { i: 1, surface: "كَبِيرٌ",   ask: ["role","case"] }
    ],
    roleOptions: ["mubtada","khabar","faʿil","mafʿul-bih","mudaf-ilayh"],  // shared chip set
    caseOptions: ["raf","nasb","jarr","mabni"],
    key: [                                  // the correct answer per token
      { i: 0, role: "mubtada", case: "raf" },
      { i: 1, role: "khabar",  case: "raf" }
    ]
  }
}
```

`sentence`, `tokens`, `roleOptions`, `caseOptions`, `key` are **all produced by the generator
(§2.3) from an annotated text** — never hand-authored in a lesson file. The lesson step only names
the text and (optionally) which words to tag.

### 2.2 The `iʿrāb` annotation schema on `texts.json`

A new **optional** array on a text entry, parallel to `words[]`. Every existing entry without it
is byte-for-byte unchanged.

```
"iʿrab": [
  { "w": 0, "role": "mubtada",     "case": "raf",  "marker": "damma",           "mahall": null,        "obj": "gr:cases-recognition" },
  { "w": 1, "role": "khabar",      "case": "raf",  "marker": "damma" },
  { "w": 2, "role": "mudaf-ilayh", "case": "jarr", "marker": "kasra" }
]
```

| field | required | meaning | values |
|---|---|---|---|
| `w` | ✔ | 0-based index into this entry's `words[]` | integer in range |
| `role` | ✔ | grammatical function | a value in `IRAB_ROLES` (controlled list, compiled from a single source of truth) |
| `case` | ✔ | case / mood, or `mabni` for a built word | `raf` · `nasb` · `jarr` · `jazm` · `mabni` |
| `marker` | ✔ | علامة الإعراب | `damma` · `fatha` · `kasra` · `sukun` · `waw` · `alif` · `ya` · `nun` (ثبوت) · `hadhf-nun` · `hadhf-illa` · `*-muqaddara` (مقدّرة variants) · `na` (for `mabni`) |
| `mahall` | – | for a `mabni` word filling a case slot | same enum as `case`, else `null` |
| `obj` | – | the learning object this token exercises | a `gr:` id; falls back to the text id |

The `marker` enum is authored **in full now** (resolved §9 Q4), not trimmed to the B1 subset: the
مقدّرة variants, the five-nouns `waw`/`alif`/`ya`, and the five-verbs `nun`/`hadhf-nun` are all
valid values even though the B1 generator only ever *asks* role + case. A default vowel used
نيابةً — `fatha` for a diptote in the genitive, `kasra` for the sound feminine plural in the
accusative — is recorded as that vowel, with `case` plus the word type disambiguating.

**Scope of v1:** `textType: "sentence"` only. `paragraph` / `dialogue` annotation is deferred to
the batch that first needs it (their sub-structure — `sentences[]` / `turns[]` — needs a
two-level `w` path; not worth designing before there's a consumer).

`IRAB_ROLES` v1 (the set the B1 labelling batch needs, extensible additively):
`mubtada` · `khabar` · `fiʿl` · `faʿil` · `naʾib-faʿil` · `mafʿul-bih` · `mudaf-ilayh` ·
`na't` (adjective) · `jarr-majrur` (شبه جملة) · `harf` (a particle, no role) ·
`ism-inna` · `khabar-inna` · `ism-kana` · `khabar-kana`.

### 2.3 The generator — `exGenParse(textId)`

Same pattern as `exGenCloze` / `exGenOrder` (M18): one exercise from an object's own fields.

- Pick a text that has an `iʿrāb` array (or the one named by `textId`).
- `sentence` = its `vowelled`; `tokens` = the annotated words; `key` = role + case per token.
- `roleOptions` / `caseOptions` = the union of this text's own annotation values plus foils drawn
  from **sibling annotated texts** (same `gr:` objective) and the controlled enums — so a wrong
  choice is always a real grammatical term, never nonsense.
- `objectResults` on completion: one per token, `objectId` = the token's `obj` or the text id.
- Returns `null` (skipped, as M18 types do) if no annotated text is available — so the milestone
  ships green against today's content, which has zero annotations.

### 2.4 UI behaviour

- The sentence renders once, RTL, `lang="ar"`, with each taggable token wrapped in a `<button>`
  (a real focusable control, not a span) styled as a chip; untagged = neutral, tagged = shows the
  chosen role/case beneath it.
- Tapping a token opens an inline picker: a **role** chip-group then a **case** chip-group
  (radio semantics — `role="radiogroup"`, arrow-key navigation, `aria-checked`). No free text.
- A **Check** button (disabled until every token has both a role and a case) grades all tokens at
  once, marks each right/wrong, and on a wrong token reveals the correct role + case **and** the
  `marker` (علامة) as a teaching moment — the learner is asked for role + case only; the marker is
  always feedback, never a question, in this recognition tier.
- One attempt, then `onResult`. Matches the `build` / `cloze` single-attempt contract.
- Keyboard + ARIA correct from the first commit (standing rule 3). New CSS scoped to
  `.exercise-host .parse-*`, token-based, listed in the PR.

### 2.5 Scoring rules

- A token is **correct** iff its chosen `role` **and** `case` both equal the key. Partial
  (role right, case wrong) counts as wrong for the object result but the UI shows which half was
  off.
- The step's overall `correct` = every token correct (same "all pairs" rule as `match`).
- `marker` and `mahall` are never scored in v1 — they surface as feedback only. (A future
  production-tier batch may add an `ask: ["marker"]` mode; the schema already carries the data.)
- Latency and per-object results flow through M18's `emitInteraction` unchanged — no new
  event shape, no new learner-state field, **no migration** (identical to how M18's `build` type
  needed none).

### 2.6 The metalanguage glossary — `term:` kind + `content/metalang.json`

- **New learning-object kind `term`**, compiled by `build-content.js` into a `METALANG` lookup
  (same mechanism as `MARKS`). Shape:

  ```
  {
    "id": "term:mabni", "kind": "term",
    "ar": "مَبْنِيّ", "translit": "mabnī",
    "name": "Built (indeclinable)",
    "def": "A word whose ending never changes for grammatical role — pronouns, most particles, some nouns and verbs. Contrast مُعْرَب.",
    "level": "B1", "skills": ["grammar"],
    "prereqs": ["term:muʿrab"], "seeAlso": ["term:mahall"]
  }
  ```

- **`content/metalang.json`** — the glossary. Authored as an English-side spec first (the exact
  `wordlists/a1.json` pattern): the term list is a curriculum plan; each entry's `ar` is a standard
  naḥw term verified against a cited reference grammar (Ryding, *A Reference Grammar of MSA*;
  al-Ghalāyīnī, *Jāmiʿ al-Durūs al-ʿArabiyya*) at authoring time — **not invented Arabic**, no
  disputable coinage. M27.0 ships **43 terms covering all B1+ functional roles** (see the stub
  file) — 10 framework · 12 case · 13 roles · 5 nawāsikh · 3 clause — with the B1 `parse`
  generator drawing its chips from a subset. Declaring the full set upfront has no downside: the
  engine only has to support any id present in the glossary, regardless of how many are used at
  launch. B2/C1 batches extend the set additively, each term cited on merge.

- **Inline tooltip only.** In `explain` and `parse` step bodies a term written as
  `{{term:mabni}}` compiles to a `<button class="term-dfn">` that opens a small popover with
  `ar` / `name` / `def`. No standalone Glossary view in M27.0 — that is a candidate for the M24 UI
  pass. The tooltip is keyboard-openable and `aria-describedby`-wired.

### 2.7 What rides on existing M18 machinery unchanged

`renderExerciseStep`, `emitInteraction`, `progress.interactionLog` (ring buffer, cap 400), the
daily-goal bump, `bumpDailyGoal`, `stepRenderers.exercise`. M27.0 adds one key to `exerciseTypes`
and one generator; it touches none of the routing.

## 3. What M27.0 does NOT do

- ❌ Add or edit anything in `content/grammar.json`, `content/curriculum.json`,
  `content/descriptors.json`, `content/lexemes.json`, `content/skills.json`, `content/levels.json`.
- ❌ Create a B1/B2/C1/C2 lesson node or flip any unit status.
- ❌ Build a standalone Glossary view, a production/marker-tagging tier, or paragraph/dialogue
  annotation.
- ❌ Revive `transform` — deferred to its own (small) scope doc, authored when B2's active
  case-manipulation batch needs it (resolved §9 Q1).
- ❌ Any change to `renderMCQ`, stroke-order, `buildAudioControl` / `playArabicAudio`, or the
  audio manifest.

## 6. `build-content.js` / `content-lint.js` changes

- Compile `content/metalang.json` → `METALANG` lookup between the auto-gen markers; validate:
  `id` unique and `term:`-prefixed, `prereqs` / `seeAlso` resolve, `level` is a real level id,
  `skills` ⊆ real skill ids.
- Validate `iʿrāb` arrays wherever present (fixtures only, for now): `w` in `words[]` range,
  `role` ∈ `IRAB_ROLES`, `case` ∈ the 5-value enum, `marker` ∈ its enum (`na` iff `case:"mabni"`),
  `mahall` null unless `case:"mabni"`, `obj` (if present) resolves to a `gr:` id.
- `{{term:…}}` references in lesson step bodies resolve to a real `term:` id.
- Coverage check for `parse` (the M18 §2 "at least one object can produce a valid item" rule):
  runs against `tools/lint-fixtures.js`, **not** real content — `exGenParse` returning `null` on
  today's un-annotated corpus is expected and fine, not an error.
- Every new rule gets a fixture in `tools/lint-fixtures.js` proving it fires (house rule).

## 9. Resolved decisions

The six questions raised in drafting, now settled. **Q1 departs from the drafting lean** (it had
recommended folding `transform` in); Q2–Q6 confirm it.

1. **`transform` is NOT folded in — deferred to its own scope doc.** M27.0 ships `parse` only.
   (a) M27.0's remit is *the smallest change that makes analytical iʿrāb teachable*; a second
   exercise type roughly doubles the render / generator / a11y / fixture surface. (b) `transform`
   ("make this منصوب word مرفوع") is a **production** task — it needs the correct re-inflected
   surface form, i.e. an authored target string per item or a morphology capability the project
   does not have as data. That is a real hidden dependency `parse` (pick a term from a chip set)
   does not carry. (c) The "duplicate enum work" concern is minor: `IRAB_ROLES` and the case enum
   are already a single source of truth, so a later `transform` milestone imports them and reuses
   the picker CSS rather than redefining anything. When B2's active case-manipulation batch needs
   it, `transform` gets a short scope doc of its own.
2. **Glossary path: `content/metalang.json`** — not `data/metalang/glossary.json`. CLAUDE.md
   mandates curriculum data under `content/*.json`, `build-content.js` only scans there, and there
   is no `data/` tree. Same call as `marks.json` / `roots.json`. (The stub already lives at this
   path.)
3. **`term` is its own learning-object kind**, not a flag on `grammar`. A term is a definition; a
   `grammar` entry is a rule with examples and `commonErrors`. Mixing them muddies `grammar.json`'s
   shape and its lint rules. `term:` compiles to its own `METALANG` lookup, exactly as
   `marks.json` → `MARKS`.
4. **The full `marker` enum is authored now** (§2.2), not trimmed to the B1 subset — the مقدّرة
   variants, the نيابة markers, the five-nouns `waw`/`alif`/`ya`, and the five-verbs
   ثبوت/حذف النون. The B1 generator only ever asks role + case; `marker` is always feedback.
   Authoring it in full now means the B2 production tier needs no schema change (I2, additive-only).
5. **Glossary surface: inline `{{term:…}}` tooltip only** in M27.0. A browsable standalone
   Glossary view is deferred to the M24 UI pass. The tooltip is keyboard-openable and
   `aria-describedby`-wired from the first commit.
6. **`obj` stays per-annotation**, optional, with text-id fallback. Per-annotation `obj` lets the
   review scheduler see *which role* a learner missed, not merely "a parse question." Optional
   means zero added authoring burden when it is not supplied.
