## 1. What this is

A new exercise type — working name **`label`** — that shows a learner a fully-vowelled sentence
with one or more words highlighted, and asks them to identify each highlighted word's grammatical
role (مبتدأ / خبر / فاعل / مفعول به / مضاف إليه, to start) and, in a fuller mode, its case
(مرفوع / منصوب / مجرور). This is the mechanism the audit's §6 "Recommended First iʿrāb Entry Point"
depends on: role-labelling on already-taught, already-vowelled sentences at late B1, full
role+case parsing at B2 (`b2-u1`, which already exists as a curriculum stub).

**This milestone builds the mechanism only.** It ships with zero new grammar points, zero new B1/B2
lesson content, and zero iʿrāb terminology added to the curriculum — those stay gated behind their
own future scope docs, exactly as the audit's Implementation Gate laid out. What this milestone
proves is that the engine *can* ask "what role does this word play?" and grade the answer — not
that any lesson yet asks it.

## 2. Why this needs its own milestone, not a quick patch

- It's a new item type in the `exerciseTypes` registry (`index.html`, alongside `choice`/`match`/
  `cloze`/`build`/`order`) — a genuine engine change, the same category of work M18 itself was.
- It needs a new content schema field (an annotation array on relevant `texts.json` entries) that
  doesn't exist anywhere in `content/*.json` today — every other exercise type is generated purely
  from fields that already exist on a lexeme/text/syllable object; this one needs new authored data.
- It is explicitly the long-pole item the audit identified: without it, any "iʿrāb lesson" the
  project ever writes can only be passive reading (an `explain` step describing a rule) — which
  defeats the entire point of a parsing skill. Content batches for B1/B2 iʿrāb should not start
  authoring against a mechanism that doesn't exist yet.
- `buildAudioControl()` / `playArabicAudio()` and every existing exercise type are explicitly
  protected elsewhere in the roadmap — this sits *next to* them, never modifies their behavior.

## 3. One correction to the audit's own framing

The audit's §8 describes this as reviving "the deferred `transform` type." Re-checking
`m18_assessment_scope.md` §2.2 directly: `transform` was scoped there as *conjugation /
pluralisation / case-change production* ("needs paired forms — only `lex:.plural` and a few verb
`notes` exist") — a learner **produces** a transformed word form. `label` is a **selection** task
(pick the right role from options for a highlighted word), mechanically closer to `choice`/`match`
than to a production exercise. They are different item shapes with different generation
requirements. This milestone proposes `label` as a genuinely new type, not a re-scoped `transform` —
`transform` itself stays exactly where M18 left it (deferred, unclaimed by this milestone).

## 4. Architectural decisions

**4.1 Registration — follows the existing contract exactly.** Every `exerciseTypes.<kind>` entry is
`{ strands: [...], render(item, host, onResult) }` (`choice` additionally sets `selfManaged: true`
and owns its own `emitInteraction` call; the rest let `renderExerciseStep` own the daily-goal +
interaction-log bookkeeping, per the comment already in `index.html` above the registry). `label`
follows the non-self-managed shape, like `match`/`cloze`/`build`/`order`.

**4.2 Content schema — additive only, on `texts.json`.** A new optional `parse` array on a text
entry (dialogue or sentence type), one entry per labelled word:
```
"parse": [
  { "word": "الطَّالِبُ", "role": "fail", "case": "raf" }
]
```
- `word` — the exact surface form as it appears in `vowelled` (or a `turns[i].ar` for dialogues),
  used to locate/highlight it. Matching by exact string, not index, so authors don't have to keep
  a position number in sync if the sentence text is ever lightly edited.
- `role` — a short closed vocabulary, seeded from exactly the five the audit's §6 soft-entry point
  names: `mubtada`, `khabar`, `fail`, `mafulbih`, `mudafilayhi`. Extending this list is a future
  batch's job (B2's five objects, the tawābiʿ, etc.) — not this milestone's.
- `case` — optional; `raf` (رفع) / `nasb` (نصب) / `jarr` (جر), or omitted entirely for a role-only
  item. Its presence is what distinguishes a B1 role-only item from a B2 role+case item — one
  schema, two difficulty levels, no separate exercise type needed for each.
- No existing text needs this field; it is purely additive and only present where a future content
  batch explicitly authors it.

**4.3 Item generation.** A `label` item is built the same way every other v1 item type already is
(per M18 §2.2's own rule: "every v1 item is generated from an existing object's own fields, no
authored question file") — from a `texts.json` entry's own `parse` array, not a separately-authored
question bank. A generator picks one or more of a text's `parse` entries, builds the multiple-choice
role (and, if `case` is present, case) options from the fixed vocabulary in §4.2 plus plausible
wrong answers drawn from that same fixed list — the same "distractors from a closed, already-defined
set" approach `choice` already uses for MCQ, not anything novel.

**4.4 Rendering.** The prompt shows the full vowelled sentence with the target word(s) visually
marked (e.g. underlined/boxed, matching how `cloze`'s blank is already marked); tapping a role (and
case, if applicable) from an option list grades it, `onResult({ correct, objectResults })` exactly
like `match`. No new rendering primitive — reuses the same button/option-list pattern `choice` and
`cloze` already use.

**4.5 Two difficulty tiers, one mechanism.** The engine does not need to know about "B1 mode" vs.
"B2 mode" — that distinction lives entirely in whether a given `texts.json` entry's `parse` array
entries carry a `case` field. A future B1 batch authors `parse` entries with `role` only; a future
B2 batch authors them with `role` + `case`. This milestone builds the mechanism generically enough
to support both from day one, without committing to authoring either.

## 5. Invariants — what must NOT change

| Must hold | Why |
|---|---|
| Zero runtime dependencies, zero runtime fetches | Standing rule 5 |
| `buildAudioControl()` / `playArabicAudio()` behavior identical | Protected system, M13/M15.5 |
| Every existing `exerciseTypes` entry (`choice`/`match`/`cloze`/`build`/`order`) behaves identically | Not this milestone's job |
| No existing `texts.json` entry is required to gain a `parse` field | Purely additive |
| No new grammar point, no new B1/B2 lesson, no iʿrāb terminology added to `content/grammar.json` or `content/curriculum.json` | Content authoring is separately gated, per the audit's Implementation Gate |
| `content/lexemes.json` / `wordlists/*.json` untouched | Out of scope |

## 6. Migration requirements

None. Purely additive — no learner-state field touched, no existing content changed.

## 7. Acceptance criteria

- `exerciseTypes.label` registered, rendering correctly for both a role-only test fixture and a
  role+case test fixture.
- `tools/content-lint.js` extended with validation for the new `parse` field (each `word` must
  actually occur in the text's `vowelled`/`turns`; `role` must be from the closed vocabulary;
  `case`, if present, must be one of the three values) — the same discipline every other schema
  field already gets.
- `tools/qa-harness.js` full regression clean; a new check exercises the `label` type end-to-end
  against at least one seeded test fixture (not real curriculum content — this milestone ships no
  curriculum content).
- `tools/a11y-audit.js` clean (new interactive elements: the option buttons).
- `npm run content:check` unchanged in every count except the new (test-fixture-only) `parse` data.

## 8. Out of scope

- Any new grammar point (`gr:cases-recognition`, `gr:mabni-muʿrab`, or anything else the audit's
  §8 proposed batch table names) — those are separate, future scope docs, gated behind this one.
- Any B1 or B2 lesson content, or any real curriculum `parse` data on existing texts.
- The naḥw metalanguage micro-glossary the audit's §4 flagged as its own dependency.
- Extending the `role` vocabulary beyond the five B1 soft-entry roles named in §4.2.
- Re-scoping or reviving the actual `transform` type — stays exactly as M18 left it (see §3).

## 9. Rollout

Plan → this branch → draft PR → review → implementation only on explicit approval, per Master
Standards (same rollout shape as M20.9 and every M21 batch). Once approved and merged, the very
next gated step per the audit is authoring B1 grammar itself (إنّ وأخواتها, relative clauses,
maṣdar, participles, subjunctive) — this milestone does not start that.

## 10. Implementation notes

Shipped exactly as designed in §4 — no deviations. `exerciseTypes.label`, `exGenLabel`, and the
`LABEL_ROLES`/`LABEL_CASES` closed-vocabulary maps sit in `index.html` alongside the other v1
types; `exGenLabel` is wired into `generateLessonSteps` the same way `exGenCloze`/`exGenOrder`
already are (fires only once a text carries a `parse` array — no current text does, so this stays
dormant in the live app exactly as intended). Rendering reuses the existing `.tile`/`.tile-bank`
classes verbatim, so it inherits the already-passing touch-target/contrast baseline with no new
CSS beyond the sentence/target-word/option-label styling itself.

One incidental bug found and fixed while adding the 3 new `content-lint.js` fixtures
(`parseword`/`parserole`/`parsecase`): `tools/lint-fixtures.js`'s "allow-list silences it" test
built the silenced rule name from a hand-enumerated ternary chain that happened to be equivalent to
just `fx.rule` for all 7 pre-existing rules, but silently fell back to `"register"` for any rule
name it didn't already special-case — which would have mis-tested the 3 new rules here. Simplified
to `[fx.rule]` directly; behavior-identical for the existing 7, correct for the new 3.
