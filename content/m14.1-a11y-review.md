# M14.1 — UI baseline: accessibility audit review

Before/after output of `tools/a11y-audit.js`, run across 2 themes × 6 breakpoints (320/375/390/768/1024/1280px) × 6 nav views (home/learn/alphabet/vocabulary/practice/progress) — 1,200 interactive-control renders and 6,434 text-node renders checked per run. See [UI_BASELINE.md](../UI_BASELINE.md) for the thresholds, tokens, and the measurement techniques this run relies on.

## Before (against unmodified `main`)

**Touch targets (< 44×44px): 706 raw findings, 33 unique controls.** All in light theme — dark theme's own copies of these same controls happened not to be flagged separately because the audit's summary de-duplicates by control+text, and every occurrence surfaced was already present in light theme.

Two of these six are not real findings: `button.speak-btn`'s and `button.speak-btn.small`'s entire text content is the emoji "🔊" with no accompanying text. Color emoji render from the font's own embedded palette, not the CSS `color` property, so a contrast ratio between "text color" and background is not a meaningful measurement for them — see UI_BASELINE.md. `tools/a11y-audit.js` was corrected to exclude emoji-only text nodes (a node mixing emoji with real text, like "🔀 Shuffle", still has its real-text portion checked) before the fixes below were verified.

## Fixes applied

1. **`--gold` (light theme)** darkened `#b8862e` → `#8a5a1f`. Fixes `badge-preview`, `shuffle-btn`'s "Shuffle" text, and every other light-theme consumer of `color: var(--gold)` on a `--gold-soft` background (`.audio-btn-slow`, `.note b`, `.voice-warning`, `.mic-warning` — checked individually, all sit on backgrounds at least as light as `--gold-soft`, so none regress). Dark theme's pairing (7.3:1) was already compliant and is untouched.
2. **`.badge-upcoming` / `.lesson-level-tag`** (light theme only): scoped `color: #5c564b` override, in place of the default `--ink-soft` (4.21:1 → ~5.2:1). Scoped rather than a global `--ink-soft` change, which is used far more widely than these two low-emphasis tags.
3. **`button.pill`** (base rule for every `.show-btn` / `.next-btn` / `.know-btn` / `.shuffle-btn` / `.review-btn`, including the smaller `.lesson-actions .pill` / `.trace-controls .pill` overrides): `min-height: 44px` + flex centering. One change, every `.pill` button app-wide fixed.
4. **`.chip`**: same `min-height: 44px` + flex-centering treatment.
5. **`.mode-switch button`** (Flashcards/Quiz/Word Bank tabs): same treatment.
6. **`.speak-btn.small`**: 34×34px → 44×44px.

A first re-run after fixes 1–6 still reported 33 touch-target "failures", all landing at 42–44px — a measurement artifact, not a real shortfall: `getComputedStyle().height` and `offsetHeight` both confirmed the CSS box was exactly 44px as specified, but `getBoundingClientRect()` (the audit's original measurement) reads up to ~1px under a flex item's true layout size inside a horizontally-scrolling (`overflow-x: auto`) row, a known Chromium sub-pixel-positioning quirk. `tools/a11y-audit.js` was corrected to measure `offsetWidth`/`offsetHeight` instead — the rounded border-box size `min-height` actually guarantees — which resolved it without any further CSS change.

## After (fixes 1–6 + both audit-methodology corrections)

The `dir="rtl"` additions (26 static + 2 JS property-assignment sites) also closed the one pre-existing `lang`/`dir` coverage gap M14.5's harness had flagged (`content/curriculum.json`'s `a1-pronouns` blurb) — see `tools/qa-harness.js`'s "lang/dir coverage" check, which was itself narrowed in this milestone to the same majority-Arabic threshold documented in UI_BASELINE.md, so it no longer flags the deliberately-unmarked inline-citation strings in `grammar.json`/`descriptors.json`/`curriculum.json`.
